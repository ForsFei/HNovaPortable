# HNova Portable — 实现方案与开发计划

> 版本 v0.1 ｜ 技术栈：.NET 10 (WPF) + MVVM + SQLite ｜ 便携优先

---

## 一、总体判断

这个项目真正的难点不在 UI，而在**"库的可移动性"**和**"不改动用户原始文件"**这两条约束下的数据一致性。因此架构上把全部复杂度收敛到三个核心对象：

| 核心对象 | 职责 | 关键不变量 |
|---|---|---|
| `LibraryRoot`（库根） | 一个可整体移动的文件夹 | 库内一切路径都相对它表达 |
| `AppEntry`（软件条目） | 一条软件记录 | 只有 `Managed` 存相对路径，`Linked` 存绝对路径并标记为不可迁移 |
| `LibraryPackage`（库包） | 导出/导入的交换格式 | 自带 manifest + 校验信息，可独立运行 |

其余功能（分类、标签、搜索、启动）都建立在这三者之上。

## 二、目录与路径策略（可移动性的根基）

### 2.1 目录结构

```text
HNovaPortable/
├─ HNovaPortable.exe
├─ Apps/                        # 托管软件（默认导入方式）
│  └─ SoftwareA/
│     └─ SoftwareA.exe
└─ Data/
   ├─ library.db                # SQLite 主库
   ├─ settings.json             # 界面/行为设置
   ├─ icons/                    # 图标缓存 <appId>.png
   ├─ cache/                    # 扫描缓存、临时文件
   ├─ backups/                  # 库备份（db + 可选 Apps）
   └─ logs/                     # 运行日志（P4 增加）
```

### 2.2 三种路径表达

| 场景 | 存储形式 | 说明 |
|---|---|---|
| 托管软件 | `Apps/SoftwareA/SoftwareA.exe` | **相对库根，永不落盘盘符** |
| 图标 | `Data/icons/<appId>.png` | 相对路径，随库迁移 |
| 引用软件 | `D:\Tools\Foo\Foo.exe` | 绝对路径；迁移后进入"待重定位"状态 |
| 工作目录 | 相对（库内） / 绝对（库外） | 导入时尽量转成相对 |

实现要点：统一用 `/` 作为库内分隔符标准化存储，读取时再按平台拼接；**禁止**在 DB 里出现 `AppContext.BaseDirectory` 的绝对路径。

### 2.3 库根的解析顺序

1. 命令行 `--root <path>`（用于测试与多库切换）
2. `Data/link.root`（内容为真实库根路径；"程序在 A、数据在 B"的进阶用法）
3. 默认：`HNovaPortable.exe` 所在目录 ← 99% 场景

启动时做**可写性探测**：若库根不可写（例如 exe 被塞进 `Program Files`），降级到 `%LOCALAPPDATA%\HNovaPortable` 并在状态栏明确提示，绝不静默失败。

### 2.4 迁移后如何"自动识别新位置"

因为托管软件路径本身是相对的，**换盘符、换机器、换文件夹名都不需要任何重写**。真正需要处理的是三种例外：

| 例外 | 处理方式 |
|---|---|
| 库根被拆散（用户只搬了 `Apps` 或只搬了 `Data`） | 启动自检：`Apps` 缺失 → 提示"定位 Apps 目录" |
| `library.db` 与当前库根不匹配（`LibraryId` 校验） | 提示"这是另一个软件库，是否切换 / 合并" |
| 引用（Linked）软件 | 迁移报告里列出失效项，提供"批量重定位父目录" |

> 结论：真正可靠的方案不是在迁移后修补路径，而是**从第一天起就不写死路径**。

## 三、数据模型

SQLite 单文件，无 EF Core（启动快、无设计时工具依赖、便于随库整体搬迁），使用 `Microsoft.Data.Sqlite` + 手写 SQL + `PRAGMA user_version` 版本迁移。

```sql
meta(key, value)                       -- schema_version / library_id / created_utc / last_migrate_utc

categories(id, name, color, sort_order, created_utc)
tags(id, name, created_utc)
app_tags(app_id, tag_id)               -- 多对多

apps(
  id TEXT PK,
  name, sort_name,
  mode INTEGER,                        -- 0 = Managed, 1 = Linked
  rel_path TEXT,                       -- 仅 Managed，形如 Apps/Foo/Foo.exe
  linked_path TEXT,                    -- 仅 Linked，绝对路径
  work_dir TEXT, arguments TEXT,
  category_id TEXT, is_favorite INTEGER,
  notes TEXT, icon_key TEXT,
  exe_version, product_name, company, description,
  size_bytes INTEGER,
  health INTEGER,                      -- 0 Ok / 1 Missing / 2 VersionChanged / 3 NeedsRelocate
  portability_flags INTEGER,            -- 位标记：含卸载器 / 无本地数据目录 / 库外引用 ...
  launch_count INTEGER, last_launch_utc,
  last_scan_utc, created_utc, updated_utc
)
```

设计取舍：
- **不做 FTS5**。库规模在数百到数千条，`LIKE` + 名前缀索引足够；FTS 的维护成本与可移植性风险不值得。
- **图标存文件不存 BLOB**。DB 保持小体积，便于按需导入导出与人工修复。
- `sort_name` 单独存（去掉前导符号、统一大小写），让排序稳定。

## 四、两种导入模式

### 4.1 语义

| | Managed（默认） | Linked |
|---|---|---|
| 文件位置 | 复制进 `Apps/<Name>/` | 原地不动 |
| DB 记录 | `rel_path` | `linked_path` |
| 可迁移 | ✅ 完整可用 | ⚠️ 需重定位；导出时可"实体化"为 Managed |
| 磁盘占用 | 翻倍 | 0 |

### 4.2 导入流程（向导，异步 + 可取消）

```text
选择来源（EXE / 文件夹 / 拖拽）
  → 分析目录（扫描 EXE、打分、识别主程序候选）
  → 用户确认（名称/分类/主程序/模式/启动参数）
  → 空间与冲突检查（目标名冲突自动改名、剩余空间）
  → 复制（字节级进度 / 可取消 / 失败回滚已复制文件）
  → 写入 DB + 抽取图标
  → 结果报告（成功 / 跳过 / 失败原因）
```

### 4.3 主 EXE 识别（避免把目录下所有 EXE 都当软件）

打分模型（命中即加分，取最高分，全部候选在向导里可切换）：

| 信号 | 权重 |
|---|---|
| 文件名 == 所在文件夹名 | +50 |
| 文件名 == 根目录名（扫描批量时） | +40 |
| 位于目录第一层（depth ≤ 1） | +20 |
| 有版本信息（ProductName/FileDescription） | +15 |
| 文件体积（对数缩放，最大 +15） | +0~15 |
| 有图标资源、非控制台子系统 | +10 |
| 名称命中黑名单（unins*、setup、update、updater、crash*、vcredist*、dxsetup、7z*、ffmpeg、*_x64 辅助进程） | 直接排除 |
| 位于 `bin/`、`lib/`、`tools/`、`resources/` 子目录 | -15 |
| 0 字节 / 无 PE 头 | 排除 |

批量扫描文件夹时，以"每个一级子文件夹 = 一个软件"为单位处理，而不是把整棵树的所有 EXE 铺平 —— 这是避免误判的关键。

## 五、整库迁移（核心特色）

### 5.1 导出的三种形态

| 形态 | 内容 | 适用 |
|---|---|---|
| **直接复制** | 整个 `HNovaPortable` 文件夹 | 推荐默认；无需任何工具介入 |
| **完整包**（folder / ZIP / 7z） | 程序文件 + `Apps` + `Data` + `export-manifest.json` | 换机即插即用 |
| **数据包** | 仅 `Data`（可选含 Apps）+ manifest | 增量备份、合并到已有库 |

压缩策略：ZIP 用 .NET 内置 `System.IO.Compression`（成熟实现，非自研算法）；`.7z` 检测同目录或 PATH 的 `7z.exe`，存在才提供选项，避免引入原生依赖。

### 5.2 导出流程

```text
选择范围（全部 / 选中 / 某分类）
  → 选项（是否把 Linked 实体化为 Managed、是否含程序文件、格式）
  → 预检：目标路径可写 / 剩余空间 ≥ 源体积 × 1.1 / 失效文件清单
  → 生成临时清单（文件数、总体积、每文件 size）
  → 复制（并行 2~4 流，字节进度，可取消，中断可续）
  → 写 export-manifest.json（libraryId、schemaVersion、条目列表、文件 size、db 的 SHA256）
  → 校验：文件数 + 总体积 + `PRAGMA integrity_check` + manifest 比对
  → 输出迁移报告（成功项、警告项、需注意的兼容性风险）
```

### 5.3 新电脑上如何继续用

- **整目录复制**：双击 exe，库根自动等于 exe 目录，路径全部自动成立。
- **导入库包**：`设置 → 导入库包` → 选择包 → 选择"新建库 / 合并到当前库"。合并时：
  1. 校验 manifest 与 `library.db`；
  2. 复制 `Apps/*` 到本库 `Apps/`，重名自动加后缀；
  3. 逐条重新计算 `rel_path`（**以复制后的实际位置为准，而不是相信包里的字符串**）；
  4. Linked 条目按"保留路径 / 标记待重定位 / 自动转换为托管"处理；
  5. 事务内写入，失败整体回滚。

### 5.4 数据不丢失的保障

- 所有写库操作在事务内完成；文件复制先写 `<name>.partial` 再改名。
- 导出前后各做一次 `integrity_check`；导出不修改源库（只读打开）。
- 恢复/合并前自动备份当前 `library.db` 到 `Data/backups/`（保留最近 5 份）。
- 删除软件时默认只删记录，删除文件需二次确认且进回收站。

## 六、跨机兼容性提示

静态无法判定注册表/AppData 依赖，采用启发式标记并在详情页与迁移报告里展示：

| 标记 | 判定 | 提示文案 |
|---|---|---|
| 含卸载器 | 目录内存在 `unins*.exe` / `Uninstall*.exe` | "疑似安装版，配置可能写在注册表" |
| 无本地数据目录 | 无 `data` / `config` / `*.ini` / `*.cfg` | "可能把配置存到 AppData" |
| 库外引用 | Linked 且不在库根内 | "迁移到新电脑后需重新定位" |
| 缺失依赖 | 记录过运行失败 | P4 起记录 |

不承诺第三方软件配置可完整迁移 —— 明确写进 UI 文案，比事后解释更有用。

## 七、架构分层

```text
HNovaPortable/
├─ Core/          AppPaths（库根解析）、PathUtils（相对/绝对互转）、Result、Logging
├─ Models/        AppEntry / Category / Tag / 枚举
├─ Data/          Database（连接+迁移）、Schema、Repositories（手写 SQL）
├─ Services/      LibraryService（自检/结构）、ImportService、ScanService、
│                 IconService、LaunchService、ExportService、ImportPackageService、
│                 BackupService、MaintenanceService、ThemeService、SettingsService
├─ ViewModels/    MainWindowVM、LibraryVM、ImportWizardVM、ExportWizardVM、SettingsVM
└─ Views/         Shell + 各大视图（MVVM，Code-behind 只留纯 UI 逻辑）
```

依赖：`CommunityToolkit.Mvvm`（源生成器，零反射）、`Microsoft.Data.Sqlite`、`Microsoft.Extensions.DependencyInjection`。其余一律不引入，保证体积和可移植性。

## 八、UI 规划

**视觉基调**：现代、科技、极简、克制。深色为主，强调色单一（科技蓝 `#3B82F6` 一档 + 悬停态），大量留白、1px 低对比描边、8~12px 圆角、无阴影堆叠。

- 主题：`Light / Dark / System`，切换实时生效（`Colors.*.xaml` 动态资源替换）。
- 窗口：自绘标题栏（`WindowChrome`），无系统边框，Win11 观感；P6 可选启用 Mica。
- 布局：
  - 左侧 236px 导航（全部 / 收藏 / 最近 / 分类 / 标签 + 底部主题与设置）
  - 顶部工具条（全局搜索、Grid/List 切换、导入、添加）
  - 主区：卡片网格（96px 图标 + 名称 + 分类/标签）或紧凑列表
  - 右侧详情抽屉：启动、打开目录、编辑、备注、兼容性提示、路径信息
- 交互：右键菜单、拖拽导入、`Ctrl+F` 聚焦搜索、双击启动。
- 长任务统一用模态进度面板（进度条 + 当前文件 + 速度 + 取消），结果统一用迁移/导入报告页。

## 九、MVP 开发顺序

| 阶段 | 内容 | 交付标准 |
|---|---|---|
| **P1 骨架** | 解决方案、DI、`AppPaths` 库根解析、DB schema + 迁移、主题资源、主窗口外壳 | 能启动，自动创建 `Apps/` `Data/` 与空库，主题可切 |
| **P2 导入** | 扫描与主程序识别、元数据/图标提取、Managed 复制（进度/取消/回滚）、Linked 引用、导入向导 | 能把一个真实软件导入并出现在列表里 |
| **P3 软件库** | Grid/List、分类/标签/收藏/搜索、详情、启动与打开目录、编辑、右键菜单 | 日常可用的软件启动中心 |
| **P4 维护** | 重扫描、失效检测、重定位、批量改名/分类、备份与恢复 | 库长期可用不腐化 |
| **P5 迁移** | 导出向导（folder/ZIP/7z）、manifest、校验、导入库包与合并、Linked 实体化 | 完成"换电脑继续用"闭环 |
| **P6 打磨** | 设置页、快捷键、Mica、日志与错误报告、空状态与引导 | 可发布 |

> 本轮先交付 **P1**，并已准备好 P2 所需的模型与库结构，避免后续返工。

## 十、已识别的主要风险

1. **图标提取**：`Icon.ExtractAssociatedIcon` 只有 32×32 且质量差 → 使用 `IShellItemImageFactory` 取 256px PNG，失败再降级。
2. **超大目录复制**：中断/断电留下半成品 → `.partial` + 临时记录 + 启动时清理。
3. **可移动介质**：WAL 模式在 U 盘/网络盘不可靠 → 保持 `journal_mode=DELETE`，`synchronous=FULL`。
4. **两个实例同时写库**：P2 起加单实例互斥（`Mutex`）+ 库文件锁提示。
5. **DB 与 Apps 不同步**（用户手工删文件夹）→ 启动时轻量抽样自检，P4 提供全量重扫描。

## 十一、便携发布与自检

### 11.1 发布方式

仓库根目录的 `publish.ps1` 一键生成便携版：

```powershell
powershell -ExecutionPolicy Bypass -File .\publish.ps1
# 可选：powershell -ExecutionPolicy Bypass -File .\publish.ps1 -Runtime win-arm64
# 可选：-Output D:\dist\HNovaPortable
```

脚本内部固定以下发布参数（不需要手工记）：

| 参数 | 值 | 原因 |
|---|---|---|
| `-c Release` | 发布配置 | 关闭调试断言，体积与启动更快 |
| `-r win-x64`（可改） | 目标 RID | 自包含，目标机不需要装 .NET 运行时 |
| `--self-contained true` | 自包含 | 便携的前提：拷走即用 |
| `PublishSingleFile=true` | 单文件 | exe 一个文件，避免同目录散落 DLL |
| `IncludeNativeLibrariesForSelfExtract=true` | 原生库内嵌 | SQLite 等原生依赖一并打包 |
| `PublishTrimmed=false` | 不裁剪 | WinForms 反射较多，裁剪风险高于收益 |
| `DebugType=none` | 无 PDB | 产物更干净 |

脚本在发布完成后补建空的 `Apps/`、`Data/` 目录，形成"exe + 两个数据目录"的最终形态。

### 11.2 产物结构

```text
publish/HNovaPortable/
├─ HNovaPortable.exe      # 单文件自包含，约 127.5 MB
├─ Apps/                  # 托管软件实体（Managed 模式复制到此）
└─ Data/                  # library.db、settings.json、icons/、exports/、backups/、cache/
```

分发方式即"整个文件夹拷走"，无需安装、无需管理员权限；库根始终等于 exe 所在目录（`AppPaths` 解析），因此换机后路径自动成立。

### 11.3 内置 UI 自检（`--selftest-ui`）

为在没有人工点击的情况下验证发布产物可运行，程序支持隐藏参数：

```powershell
.\HNovaPortable.exe --selftest-ui
```

行为：依次构造主窗口、导入窗口、导出窗口，记录尺寸、分类数、扫描结果与导出目标路径，写入 `Data/cache/uitest.log`，随后自动退出（退出码 0 表示全部通过）。

最近一次在发布目录实测的结果：

```text
[main]   loaded=True size=1360x880 apps=0 nav=2 status=软件库为空，点击「导入软件」开始
[import] loaded=True size=1020x720 categories=8
[import] items=1 selected=7-Zip main=7zFM.exe status=扫描完成：1 个软件候选
[export] loaded=True size=760x760 apps=0 target=...\publish\HNovaPortable-export-20261118
[done]   all windows loaded
```

该自检覆盖了空库引导文案、8 分类渲染、扫描识别（7-Zip → `7zFM.exe`）与导出目标命名，可作为每次发版前的冒烟测试。

> 注意：自检会在产物目录产生 `Data/library.db`、`Data/settings.json`、`Data/cache/uitest.log`。正式分发前清空 `Data/`、`Apps/` 内容（保留两个空目录），即为干净的首次运行状态。
